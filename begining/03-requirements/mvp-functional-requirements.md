# Astronaut MVP — функциональные требования

Версия 0.1 · 29.10.2026 · черновик для аналитика и команды

Пометки: **[M]** — обязательно в MVP, **[S]** — желательно в MVP, **[L]** — после MVP. **[гипотеза]** — не проверено на клиентах.

## 1. Что продаём одной фразой
Платформа, которая переносит данные между 1С, сайтом на 1С-Битрикс, Битрикс24, amoCRM, PostgreSQL, MySQL, MongoDB, S3 и любым REST API, не теряет сообщения и собирает единый справочник контрагентов. Поток можно собрать мышкой, через AI-чат, в Terraform или кодом.

Модель потока: **FROM → BY → TO**.
- FROM, TO: 1С, 1С-Битрикс, Битрикс24, amoCRM, PostgreSQL, MySQL, MongoDB, S3 API, REST API.
- BY: low-code, AI-чат в интерфейсе, Terraform-провайдер, данные как код (SDK на Go, Python, PHP, TypeScript).
- Плюс MDM: золотая запись контрагентов.

## 2. Кому продаём
- **Покупатель:** ИТ-директор или руководитель 1С-направления в компании на 200–2 000 сотрудников (торговля, дистрибуция, производство, логистика), у которой 4–10 систем и 1С в центре. [гипотеза]
- **Канал:** интеграторы и франчайзи 1С, которые делают такие интеграции руками. [гипотеза]
- **Пользователи внутри клиента:** разработчик интеграций (1С или бэкенд), аналитик, DevOps, стюард данных, наблюдатель (руководитель).
- **Не берём в MVP:** госсектор и КИИ (нужен реестр ПО), банки.

## 3. Бизнес-кейсы, которые закрывает MVP
Каждый кейс — то, что продаётся отдельно и показывается на пилоте.

### B1. CRM и учёт видят одних клиентов
**Маршрут:** 1С (УТ/ERP/КА) ↔ Битрикс24 или amoCRM.
**Что делает:** контрагенты и контакты из 1С в CRM при каждом изменении; ответственный менеджер сопоставляется по email; выигранная сделка в CRM создаёт заказ клиента в 1С; статус оплаты и отгрузки возвращается в сделку.
**Боль сейчас:** ручной перенос, дубли компаний в CRM, менеджер не видит долг и отгрузки.
**Критерий успеха пилота:** изменение контрагента в 1С видно в CRM за ≤ 1 минуту; 0 потерянных сделок за 2 недели.

### B2. Сайт продаёт то, что есть на складе
**Маршрут:** 1С ↔ 1С-Битрикс (интернет-магазин).
**Что делает:** каталог, цены по типам цен, остатки по складам из 1С на сайт по расписанию (только изменения); заказы с сайта в 1С сразу по вебхуку; статусы заказа обратно на сайт.
**Боль сейчас:** стандартный обмен по расписанию раз в час, падает молча, заказы теряются или дублируются.
**Критерий успеха:** остатки на сайте отстают от 1С не больше чем на 10 минут; каждый заказ с сайта либо в 1С, либо в очереди недоставленных с понятной причиной.

### B3. Один справочник контрагентов (MDM)
**Маршрут:** 1С:УТ + 1С:ERP + Битрикс24 + amoCRM → MDM → обратно во все системы.
**Что делает:** проверяет ИНН/КПП, приводит телефоны и адреса к единому виду, находит дубли, автоматически объединяет точные совпадения по ИНН+КПП, похожие отдаёт стюарду, собирает золотую запись по правилам и раздаёт исправления обратно.
**Боль сейчас:** один клиент заведён в 3–4 системах по-разному, отчёты по клиентам не сходятся.
**Критерий успеха:** доля дублей падает в разы (замер до и после), у каждой записи в системах есть ссылка на золотую запись.

### B4. Данные для отчётов без ручных выгрузок
**Маршрут:** 1С или PostgreSQL/MySQL/MongoDB → PostgreSQL (хранилище), MongoDB → S3.
**Что делает:** продажи, остатки, движения из 1С в хранилище по расписанию; события и логи из MongoDB в S3 пакетами (CSV/JSON, Parquet [S]).
**Критерий успеха:** ежедневная выгрузка без участия человека, при сбое — повтор и уведомление.

### B5. Переезд со старой системы
**Маршрут:** MySQL/MongoDB → PostgreSQL или 1С.
**Что делает:** разовая или поэтапная миграция с маппингом, проверками и дедупликацией через MDM, отчёт «перенесено / отклонено и почему».
**Критерий успеха:** каждая исходная запись либо перенесена, либо в отчёте об отклонённых.

### B6. Внешние сервисы в учёте
**Маршрут:** REST API (доставка, банк, маркетплейс) ↔ 1С.
**Что делает:** импорт OpenAPI, авторизация, пагинация, соблюдение лимитов, повторы; статусы доставки и платежи в 1С.
**Критерий успеха:** при лимите 429 или недоступности сервиса ни одно сообщение не теряется.

## 4. Состав MVP по модулям

### 4.2. Потоки
| ID | Требование | Приоритет |
|---|---|---|
| FLW-1 | Поток = источник (подключение + объект + фильтр) + запуск + шаги + маппинг + получатель (подключение + объект + ключ upsert) + политика доставки | M |
| FLW-2 | Запуск: при изменении, по расписанию (cron), входящий вебхук, вручную | M |
| FLW-3 | Шаги: фильтр, маппинг полей, преобразование значений (функции и таблицы соответствия), поиск по справочнику получателя (lookup), значение по умолчанию, проверка контракта, разбиение и пакетирование | M |
| FLW-4 | Стандартные функции: ИНН/КПП/ОГРН-проверка, телефон в +7, email в нижний регистр, даты и часовые пояса, числа и валюты, адрес через внешний сервис [S] | M |
| FLW-5 | Свой шаг кодом (функция на TypeScript или Python в песочнице) | S |
| FLW-6 | Версии потока: черновик → версия; дифф между версиями; откат на любую версию | M |
| FLW-7 | Тестовый запуск на синтетических или выбранных записях без записи в получателя (dry run) и с записью в окружение «Разработка» | M |
| FLW-8 | Шаблоны для кейсов B1–B6: готовый поток с типовым маппингом, который правится | M |

### 4.3. Способы сборки (BY)
Все четыре способа редактируют **одну и ту же модель потока**. Изменение в одном видно в остальных.

| ID | Требование | Приоритет |
|---|---|---|
| BY-1 | **Low-code:** визуальная траектория FROM → шаги → TO, таблица маппинга с выбором полей из метаданных, настройки шагов формами | M |
| BY-2 | **AI-чат:** предложения маппинга, объяснение ошибки, генерация синтетических тестовых данных. Каждое предложение — диф с уверенностью, кнопки «Применить» / «Отклонить». Правила AI — раздел 4.8 | M |
| BY-3 | **Terraform:** провайдер `astronaut` с ресурсами `astronaut_connection`, `astronaut_flow`, `astronaut_mdm_rule`; import существующих объектов; plan показывает дифф | M |
| BY-4 | **SDK** на TypeScript и Python [M], Go и PHP [S]: описать поток кодом, прогнать тесты локально, выкатить | M/S |
| BY-5 | **CLI** `astro`: login, init, test, diff, deploy, replay | M |
| BY-6 | Конфликт правок из UI и из кода: выкат из кода блокируется, если в UI есть невыкаченный черновик, и наоборот; показывается дифф | M |
| BY-7 | Экспорт потока из UI в Terraform или SDK-код | S |

### 4.4. Доставка и надёжность
| ID | Требование | Приоритет |
|---|---|---|
| DLV-1 | Каждое сообщение записывается в журнал до обработки; журнал реплицируется минимум на 2 узла | M |
| DLV-2 | Идемпотентность: ключ сообщения; повтор не создаёт дубль в получателе (upsert по ключу) | M |
| DLV-3 | Повторы с экспоненциальной задержкой, лимит попыток настраивается; уважение 429 и Retry-After | M |
| DLV-4 | Очередь недоставленных: сообщение хранится с причиной ошибки; повтор одного, выбранных или всех | M |
| DLV-5 | Порядок сообщений по одному ключу (например, по одному контрагенту) сохраняется | M |
| DLV-6 | Кластер от 3 узлов; падение узла не теряет сообщения и не меняет адрес для внешних систем | M |
| DLV-7 | Документированные гарантии доставки (at-least-once + идемпотентная запись) и тесты отказов в CI | M |

### 4.6. Мастер-данные (MDM)
В MVP — сущность «Контрагенты». «Номенклатура» — [L].

| ID | Требование | Приоритет |
|---|---|---|
| MDM-1 | Модель сущности: поля, типы, обязательность, история версий записи | M |
| MDM-2 | Загрузка записей из потоков (любой FROM) с сохранением ссылки на источник; кросс-таблица ID «запись в системе ↔ золотая запись» | M |
| MDM-3 | Очистка и проверка: ИНН (контрольная сумма), КПП, ОГРН, телефоны к +7, email, организационно-правовая форма, кавычки | M |
| MDM-4 | Адреса к ФИАС и обогащение по ЕГРЮЛ через внешний сервис (например, DaData) — подключается как REST | S |
| MDM-5 | Правила поиска совпадений: точные (ИНН+КПП) → автообъединение; ИНН совпадает, КПП разные → в очередь (филиал); нечёткие (название ≥ порога + адрес/телефон) → в очередь | M |
| MDM-6 | Два порога: автообъединение и «на проверку»; ниже второго — не дубль | M |
| MDM-7 | Правила выживания по каждому полю: доверенный источник, самое свежее, самое полное, чаще всего встречается; приоритет источников | M |
| MDM-8 | Очередь стюарда: сравнение записей по полям, выбор значения кликом, «Объединить», «Это разные компании», «Разделить» | M |
| MDM-9 | Отмена объединения в течение 30 дней; исходные записи не удаляются, старые ID остаются псевдонимами | M |
| MDM-10 | Раздача золотой записи обратно в системы потоком «Раздача мастер-данных» | M |
| MDM-11 | Метрики качества: доля дублей, полнота, валидность, размер очереди | M |
| MDM-12 | Заявки на создание и изменение записи с согласованием | L |
| MDM-13 | Номенклатура: шаблоны наименований, ОКПД2, ТН ВЭД, ОКЕИ | L |

### 4.8. Правила для AI (жёсткие)
| ID | Требование | Приоритет |
|---|---|---|
| AI-1 | AI не участвует в доставке и обработке сообщений. Платформа полностью работает с выключенным AI | M |
| AI-2 | Модель получает только метаданные (схемы, названия и типы полей), журнал ошибок без содержимого и синтетические примеры. Передача содержимого сообщений заблокирована политикой | M |
| AI-3 | AI ничего не применяет сам: любое предложение — диф, применяет человек с нужной ролью | M |
| AI-4 | Каждое предложение и решение по нему пишется в журнал | M |
| AI-5 | Выбор модели: локальная в контуре клиента или облачная в российском облаке; выключатель на уровне организации | M |
| AI-6 | В MDM AI может только предложить кандидата в очередь стюарда, никогда не объединяет записи | M |

## 5. Нефункциональные требования (цели MVP, уточнить замерами)
- **Развёртывание:** у клиента (on-prem) на Linux: Debian, Ubuntu, Astra Linux, РЕД ОС; Docker-образы. Облачная часть — только в российском облаке.
- **Производительность [гипотеза]:** 1 000 сообщений в секунду на кластер из 3 узлов; задержка p95 до 1 секунды для потоков «при изменении».
- **Надёжность:** падение одного узла из трёх — без потери сообщений и без смены адреса; потеря диска одного узла — без потери данных.
- **Хранение:** журнал сообщений — 14 дней по умолчанию, настраивается.
- **Безопасность:** TLS везде, секреты в зашифрованном хранилище, журнал действий неизменяемый.
- **Импортонезависимость:** без зарубежных облаков и сервисов в работе платформы; подготовка к реестру российского ПО.

## 6. Что не входит в MVP
- Коннекторы SAP, Kafka, RabbitMQ, ЭДО, маркетплейсов отдельными модулями (кроме как через REST API).
- Номенклатура в MDM, заявки на изменение мастер-данных.
- Визуальный редактор сложных бизнес-процессов с ветвлениями и циклами.
- Сертификация ФСТЭК, реестр ПО (подготовка идёт параллельно).
- Мультиарендное облако (SaaS для многих клиентов на одном кластере).
