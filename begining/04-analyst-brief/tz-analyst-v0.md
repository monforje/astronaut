# ТЗ для аналитика: подготовка требований к MVP Astronaut

Версия 0 · 29.10.2026 · поверхностное, задача аналитика — превратить его в полноценное ТЗ

## 1. Контекст
Astronaut — платформа интеграции данных и мастер-данных для российского среднего бизнеса. Конкурент-ориентир — DATAREON (лидер по числу внедрений), рядом «1С:Шина», Digital Q.Integration, open source (NiFi, n8n).

Что уже есть:
- Функциональные требования верхнего уровня: `03-requirements/mvp-functional-requirements.md`.
- Кликабельный прототип интерфейса: `05-mvp-ui/index.html`. Логики и бэкенда нет.
- Исследования рынка и конкурента: `01-research/`, `02-strategy/`.

Модель продукта: **FROM → BY → TO**.
- FROM / TO: 1С, 1С-Битрикс, Битрикс24, amoCRM, PostgreSQL, MySQL, MongoDB, S3, REST API.
- BY: low-code, AI-чат, Terraform, SDK (Go, Python, PHP, TypeScript).
- MDM: золотая запись контрагентов.

Принцип, который нельзя нарушать: **AI — вспомогательная функция**. Он не участвует в доставке, не видит содержимое сообщений и ничего не применяет сам.

## 2. Цель работы аналитика
Подготовить ТЗ, по которому команда разработки сможет оценить и сделать MVP за один цикл, а продажи — провести пилоты по кейсам B1–B6.

## 3. Что нужно сделать

### 3.1. Проверить бизнес-кейсы на реальных людях
- Провести 8–10 интервью: 4–5 интеграторов 1С, 4–5 ИТ-директоров или руководителей 1С среднего бизнеса.
- По каждому кейсу B1–B6 выяснить: как делают сейчас, сколько это стоит (часы, деньги), что ломается чаще всего, кто принимает решение о покупке, готовы ли платить и сколько.
- Итог: подтверждённый список кейсов с приоритетом и цитатами; кейсы без спроса — убрать из MVP.

### 3.2. Детально описать коннекторы
Для каждого из 9 коннекторов:
- поддерживаемые версии (1С 8.3.x и конфигурации, версии СУБД, API Битрикс24 и amoCRM);
- объекты для чтения и записи в MVP;
- способ отслеживания изменений и его ограничения (например, MongoDB change streams требуют replica set);
- авторизация и хранение секретов;
- лимиты API и поведение при их превышении;
- типовые ошибки и как их показываем пользователю.

Для 1С отдельно: вариант с расширением и вариант только через HTTP-сервисы (для клиентов с запретом на изменение конфигурации).

### 3.3. Описать модель потока
- Сущности: подключение, поток, версия, шаг, маппинг, политика доставки, сообщение, окружение.
- Жизненный цикл потока: черновик → тест → выкат → откат.
- Каноническое представление потока, общее для UI, Terraform и SDK (предложить формат, JSON Schema или аналог).
- Правила разрешения конфликтов между правками в UI и в коде.

### 3.4. Описать надёжность доставки
- Гарантии доставки и идемпотентность по каждому типу получателя: где upsert возможен, где нет (например, документы 1С).
- Политика повторов, очередь недоставленных, порядок по ключу.
- Сценарии отказов, которые проверяем: падение узла, потеря диска, недоступность получателя, лимит 429, изменение схемы источника.

### 3.5. Описать MDM для контрагентов
- Модель золотой записи и кросс-таблица ID.
- Правила очистки и проверки (ИНН, КПП, ОГРН, телефоны, адреса).
- Правила поиска совпадений и пороги, правила выживания по полям.
- Сценарии стюарда: объединить, «это разные», разделить, отменить.
- Раздача золотой записи обратно в системы: какие поля, какие системы, что делать с конфликтами.
- Отдельно: юрлицо, ИП, филиал и грузополучатель — разные сущности, правила их различения.

### 3.6. Описать роли и права
Матрица «роль × действие × окружение» для ролей: Администратор, Разработчик интеграций, Стюард данных, Наблюдатель. Отдельно: доступ к содержимому сообщений и к AI-функциям.

### 3.7. Описать AI-функции
Для трёх функций (маппинг, объяснение ошибки, тестовые данные):
- что получает модель на вход (точный перечень, без содержимого сообщений);
- формат предложения (диф, уверенность);
- как пользователь принимает и отклоняет;
- что пишется в журнал;
- поведение при выключенном AI.

### 3.8. Нефункциональные требования
Целевые значения производительности, задержки, объёма журнала, срока хранения. Требования к развёртыванию (ОС, Docker, кластер). Требования для подготовки к реестру российского ПО.

## 4. Что сдать (артефакты)
1. **Сценарии использования** по кейсам B1–B6: основной и альтернативные потоки, ошибки.
2. **Схемы процессов** для потока, выката, работы стюарда (BPMN или аналог).
3. **Модель данных** платформы: сущности, атрибуты, связи.
4. **Спецификации коннекторов** по шаблону из 3.2.
5. **Типовые маппинги** для кейсов B1 и B2 (1С:УТ ↔ Битрикс24, 1С:УТ ↔ 1С-Битрикс): таблица полей с преобразованиями.
6. **Матрица ролей и прав.**
7. **Критерии приёмки** для каждого требования из `mvp-functional-requirements.md` с ID.
8. **Протоколы интервью** и сводка выводов.
9. **Список открытых вопросов и решений** с ответственными.

## 5. Как работать с прототипом
- Открыть `05-mvp-ui/index.html` в браузере.
- Прототип показывает экраны и переходы, но не логику: проверки, сохранения и AI-ответы заготовлены.
- Все расхождения прототипа с требованиями фиксировать списком: прототип можно переделать.

## 6. Ограничения
- В MVP не входят: номенклатура в MDM, SAP, Kafka, ЭДО, мультиарендное облако.
- Целевой клиент — коммерческий средний бизнес, не госсектор и не КИИ.
- Продукт ставится у клиента (on-prem); облачная часть только в российском облаке.
